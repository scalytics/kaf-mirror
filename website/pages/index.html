Open source. Apache 2.0.

Kafka backup you can watch, audit and trust.

One server binary with a dashboard. Exact copies, in partition order, with idempotent writes, and a resume from the last committed offset after a restart. RBAC, an audit trail, compliance reports, and Replication halt (tech preview) if a bad write starts to spread. Apache 2.0, with no license key.

A replica is not a backup.

A replica follows every change, including deletes, bad writes and anything done with stolen producer credentials. For a backup, copy into a target that your producers cannot touch, on separate credentials. KafScale, a Kafka-compatible broker that stores immutable segments in S3, is one option. Any Kafka-compatible target is configured the same way. The KafScale steps are in the backup guide.

What's new in 2.0.0

kaf-mirror 2.0.0 is out. This is a major release with breaking changes, so read the upgrade notes and the Breaking section of the changelog before you upgrade. The GitHub release has the binaries and the image. Pull ghcr.io/scalytics/kaf-mirror:v2.0.0 (linux/amd64 and linux/arm64), or download mirror-cli for Linux, Windows, macOS Intel and Apple Silicon.

  • Recreated topics. A job follows a source topic that is deleted and created again by its Kafka topic ID, and copies the new topic from its earliest offsets. A deleted topic that is not created again stays listed in missing_source_topics, and the job stays active.
  • Job selection. Job commands refuse to run until you pick a job or pass the id. They no longer call the API with an empty id.
  • Shell completion. mirror-cli and admin-cli complete in Bash, Zsh, Fish and PowerShell. The interactive shell restores the terminal when it exits. See the shell completion guide.
  • Security. Password flags are gone from login and users add. Tokens, keys and passwords are not printed. The token file is always mode 0600. CORS now ships as http://localhost:8080 instead of *.
  • Helm on kind and k3s. If the default storage does not honor fsGroup, pass a values file with volumePermissions.enabled: true. See the Kubernetes guide.
  • Docs. The README is a short front page. The rest is in docs/, including getting started, Kubernetes, administration and security.
  • Replication halt (tech preview). Off by default and admin-only. Freezes the copy if the source looks compromised. See docs/protection.md.
  • Version in the image. A published image reports v2.0.0 in the API, the UI and --version. A local build reports dev.

See it run

Two Kafka-compatible clusters (Redpanda in the demo), one kaf-mirror, about two minutes. The terminal installs the mirror-cli Bash completion script and uses Tab to complete commands.

  1. Start two Redpanda brokers and kaf-mirror with docker compose up -d.
  2. Log in with mirror-cli. The password prompt is masked.
  3. Add a source cluster and a target cluster.
  4. Produce three orders to the source, create a job for the orders topic and start it.
  5. Produce two more orders, then read all five from the target cluster.
  6. Check the job status and lag.

What you get

One binary, a dashboard

The server is one binary with a web dashboard. You do not need a Kafka Connect cluster. Jobs, lag, health and compliance are in the UI and in mirror-cli. See how that compares with MirrorMaker 2, Confluent Replicator and Cluster Linking.

Exact copies

Keys, values, headers, partitions and timestamps are kept. Records stay in partition order. Writes are idempotent by default, so a retried produce is not stored twice. Source offsets are committed only after the target acknowledges the write, and a restart resumes from the last committed offset. See what a copied record keeps and resilience.

Jobs that follow a recreated topic

When a source topic is deleted and created again, the job follows the new topic by its Kafka topic ID and copies it from its earliest offsets. The job stays active. Brokers without topic IDs, before Kafka 2.8, keep following the topic by name.

Ops and compliance controls

RBAC with admin, operator, monitoring and compliance roles. An audit trail and scheduled compliance reports. Replication halt (tech preview) is off by default and admin-only: it can stop a bad write spreading to the backup. See RBAC and Replication halt.

Apache 2.0

kaf-mirror is Apache 2.0. There is no license key to start it. Confluent Replicator and Cluster Linking are commercial Confluent features. The details, with links to their docs, are on the comparison page.

Web UI

A tab-based dashboard with Operations, Health, Executive and Compliance sections. The UI polls the API every 30 seconds, reads the user's permissions from GET /auth/me, and hides buttons the user cannot use. It fits phone screens down to 390px.

TLS and mTLS

TLS is used when security.protocol is SSL or SASL_SSL, and always for the confluent and azure providers. Production requires TLS unless server.allow_insecure is set. SASL PLAIN, SCRAM and Kerberos (GSSAPI) are also supported.

Helm

The supported way to run kaf-mirror in Kubernetes is the chart in deploy/helm/kaf-mirror. A default install starts and answers /health on storage that honors fsGroup. On kind or k3s, turn on volumePermissions with a values file.

Also in the current docs

REST API and CLIs

A Fiber REST API manages the application. admin-cli is for bootstrap and emergency maintenance. mirror-cli is the management CLI, with shell completion for Bash, Zsh, Fish and PowerShell. The API docs are at /docu/swagger/ when kaf-mirror is running. The CLI reference and the shell completion guide are in the docs.

Configuration

Base configuration comes from a default.yml file. Runtime changes such as jobs, clusters, topic mappings and users are stored in SQLite. Every config key and environment variable is listed in the configuration reference.

Metrics and lag

Every running job reports counters every 10 seconds, including messages copied, bytes transferred, errors, tombstones and current lag. Job metrics are stored in SQLite. The process /metrics endpoint serves only Go runtime metrics.

AI insights, opt-in

Off until ai.provider is set. Without a provider, kaf-mirror makes no AI requests. See the AI analysis docs.

Where it is used

  • Backup. Copy topics into a target your producers cannot reach, for example KafScale on S3. The steps are in the backup guide. See also Kafka backup vs replication.
  • Hot standby. Use kaf-mirror between two Kafka-protocol clusters when you want a live copy you can fail over to.
  • DORA and NIS2. The audit trail and scheduled compliance reports help show how the copy is run and checked. See the Kafka DORA and NIS2 checklist.
  • Migration and failover drills between Kafka-protocol clusters, with same-name, exact or regex topic mapping.
