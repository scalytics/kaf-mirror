Comparison

kaf-mirror compared with MirrorMaker 2, Replicator and Cluster Linking.

A factual look at how you run a Kafka copy, what is preserved, and how the tools are licensed. Where another product does more, that is stated. Sources are linked at the end.

kaf-mirror

kaf-mirror is a single server binary with a dashboard. A job consumes from a source cluster and produces to a target. Writes are idempotent by default. Source offsets are committed only after the target acknowledges the write, so a restart resumes from the last committed offset. It does not keep source offsets on the target, and it does not copy consumer groups or ACLs. It does not do point-in-time restore of a topic. For a backup that a bad delete on the source cannot reach, copy into a target your producers cannot touch, for example KafScale on S3.

MirrorMaker 2

Apache Kafka's MirrorMaker 2 is built on the Kafka Connect framework. It can run as a dedicated MirrorMaker cluster or as connectors in an existing Kafka Connect cluster. Administrators define replication flows in a properties file, typically connect-mirror-maker.properties. Official docs list topic and configuration replication, consumer group and offset replication, ACL replication, preserved partitioning, automatic detection of new topics and partitions, and a range of metrics, including end-to-end replication latency. It is part of Apache Kafka and is licensed under Apache 2.0. It does not ship a kaf-mirror-style dashboard, RBAC roles, audit trail or compliance reports.

Confluent Replicator

Confluent Replicator copies topics between Kafka clusters. It runs as a Kafka Connect connector or as a Replicator executable. Confluent's license documentation lists Replicator under the Confluent Enterprise License. On Confluent Platform 5.5.0 and later, Confluent documents that Replicator requires a license key and that there is no trial period on those versions. It is a commercial product with a different operations model from an Apache 2.0 binary you start yourself.

Cluster Linking

Cluster Linking is built into Confluent Server and Confluent Cloud. Confluent documents byte-for-byte replication with globally consistent offsets and identical content across partitions. It is included at no extra licensing cost beyond a Confluent Enterprise license subscription. The destination cluster must be Confluent Server (Confluent Platform 7.8.x or later) or Confluent Cloud; the source can be Kafka, Confluent Server or Confluent Cloud. That offset-preserving design is something kaf-mirror does not claim: kaf-mirror keeps record fields and partitions, and the target broker assigns new offsets.

uReplicator

uReplicator is Uber's open source Apache Kafka replicator, published on GitHub. Uber describes it as a Kafka replicator that uses Apache Helix for worker management, designed for their scale. It is a different architecture from a single server binary with a dashboard. This page does not attempt a feature-by-feature match, because Uber's public document is the project README rather than a product manual at the same level as the Apache Kafka and Confluent docs above.

When to use what

  • kaf-mirror when you want a Kafka backup or a live copy you can operate from a dashboard, with RBAC, an audit trail and Apache 2.0, including targets that are not Confluent Server.
  • MirrorMaker 2 when you already run Kafka Connect and you want consumer group and ACL replication as part of Apache Kafka.
  • Confluent Replicator when you are on Confluent Platform and have an Enterprise license for Replicator.
  • Cluster Linking when the destination can be Confluent Server or Confluent Cloud and you need byte-for-byte mirrors with consistent offsets.
