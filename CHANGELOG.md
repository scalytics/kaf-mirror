# Changelog

All notable changes to this project are documented here.

## [Unreleased]
### Breaking
- `admin-cli backup` no longer overwrites an existing file. The command fails and leaves the file alone. Use a new path or delete the old file first (#68).
- `admin-cli restore` and `import` fail with a non-zero exit status when there is no terminal to confirm. Scripts must pass `--yes`. Before, they printed "cancelled" and exited 0 (#68).
- `admin-cli tokens reset` does the same: it needs `--yes` without a terminal, and a missing confirmation is a non-zero exit (#68).
- `mirror-cli users add --password` is removed. The flag was never read. The generated password is written to a mode `0600` temp file and only the path is printed (#74).
- `mirror-cli whoami` no longer prints the API token. It shows the username and role (#74).
- `mirror-cli login`, `users reset-password`, `clusters remove`, `jobs delete` and other prompts that used to print "cancelled" and exit 0 when stdin is not a terminal now exit with a non-zero status. The destructive commands take `--yes` for scripts (#73, #74).
- List endpoints answer `[]` when there is nothing to list, and `GET /api/v1/jobs/{id}/lag` answers `{}`. Before, many of them answered `null`. A client that checked for `null` must check for an empty list (#72).
- `POST /api/v1/clusters/{name}/restore` sets the cluster status to `unknown` and starts a connection check, which sets `active` or `unreachable`. Before, it set `active` without a check (#70).
- The audit trail in the compliance CSV has a new `Action` column between `Initiator` and `Details`, and its title is `AUDIT TRAIL (Changes)` (#75).
- `mirror-cli login --password` is removed, so a password never ends up in the shell history or the process list. `login` asks without echo, or reads the first line of stdin when there is no terminal (#76).
- `admin-cli import database --merge` is removed. It was never implemented and only exited with an error (#76).
- `admin-cli users add --password` is removed, so a password never ends up in the shell history or the process list. `users add` asks without echo, or reads the first line of stdin when there is no terminal (#76).
- `configs/default.yml`, `configs/docker.yml` and the Helm chart value `config.server.corsAllowedOrigins` ship `["http://localhost:8080"]` instead of `["*"]`. The web UI is served by kaf-mirror and does not need CORS. A browser app on another origin must be added to `server.cors.allowed_origins` (#76).
- `DELETE /api/v1/jobs/{id}` answers HTTP 404 with `Job not found` when the job does not exist. Before, it answered HTTP 204. Clients that treated 204 as "already gone" must handle 404 (#76).
- A job needs at least one topic mapping, and a cluster update needs brokers. `POST /api/v1/jobs` answers HTTP 400 when `name`, `source_cluster_name` or `target_cluster_name` is empty or only spaces, or `topic_mappings` has no entry, and HTTP 404 with `Source cluster not found` or `Target cluster not found` when a cluster does not exist. `PUT /api/v1/jobs/{id}` answers 404 for an unknown cluster too. Before, an empty job was created and an unknown cluster gave HTTP 500 (#88).
- `POST /api/v1/clusters` answers HTTP 400 when `name` is empty, only spaces or contains `/`, or `brokers` is empty, and `PUT /api/v1/clusters/{name}` answers 400 when `brokers` is empty. A cluster or job name that already exists answers HTTP 409 instead of 500. `DELETE /api/v1/clusters/{name}` answers HTTP 404 for an unknown cluster instead of 202 (#88).
- `error_count` now also counts source fetch errors, one for each partition in each fetch that returns an error, so it can grow without failed produce attempts (#87).

### Fixes
- kaf-mirror starts on a data directory it does not own, such as a kind or k3s `local-path` volume (`root:root`, mode `0777`), a volume with `fsGroup` 101 or a Docker bind mount the container user can write to. It sets the data directory to mode `0700` only when it owns it, and otherwise leaves the mode alone and logs a warning when the directory is open to the group or others. The database, `-wal`, `-shm` and lock files are still created with mode `0600`, and an existing database file of another user that the group or others can read still stops the start. A start that fails for any reason other than a held lock no longer says a restore or another kaf-mirror process may be the cause, and a permission error names the UID and GID that need write access. The Helm chart sets `fsGroupChangePolicy: OnRootMismatch`. This was a regression from #80 that made the default Helm install crash on kind (#85).
- A job whose source topic was deleted and created again switches to the new topic and keeps copying. kaf-mirror notes the Kafka topic ID of each source topic from the source metadata when the job starts, when a topic is added, and from any successful fetch, including an empty one, reads it again every 10 seconds and when a fetch answers `UNKNOWN_TOPIC_ID`, and on a new ID commits the earliest offsets of the new topic for the job consumer group and subscribes to the topic again, so it copies the new topic from its earliest offsets. It logs the old and new topic ID, and `source_topic_recreations` in `GET /api/v1/jobs/{id}/metrics/current` and the Prometheus gauge `kaf_mirror_source_topic_recreations` count the switches since the job started. A source topic that was deleted and not created again keeps the job `active`, adds 1 to `error_count` for each check, is listed in `missing_source_topics` and sets the Prometheus gauge `kaf_mirror_incident_source_topic_missing`, and is logged at most once every 30 seconds. Brokers without topic IDs keep following the topic by name. Before, the job stayed `active`, copied nothing and logged about 1,100 errors per second with `error_count` 0. Fetch errors are counted in `error_count`, the same error of a partition is logged at most once every 30 seconds with the number left out, and a fetch with only errors waits from 100ms, doubling up to 5s, before the next one, and does not wait after a fetch without errors. The protection auto-halt still counts only produce errors (#87).
- A fetch of the recreated topic that comes before the topic ID check no longer replaces the stored topic ID, so the switch, its log line and `source_topic_recreations` still happen. Records of the deleted topic that were fetched before a switch are not committed after it, so they cannot move the committed offset of the new topic past its earliest offset. Switch commits and the commits of the consumer do not run at the same time (#87).
- Two requests that create the same cluster or job at the same time answer HTTP 409 for the second one. Before, the second cluster answered HTTP 500 and the second job was stored with the same name. `POST /api/v1/clusters` removes leading and trailing spaces from `name`, as job create does for cluster names, so a job can refer to the cluster (#88).
- `GET /api/v1/jobs/{id}/metrics/current` returns the live `source_stalled`, `target_stalled`, `critical_lag`, `high_error_rate` and `error_spike` of the last report of the running job. Before, they were always `false`, also while the log said the source stalled. A job that is not running returns them as `false` (#86).
- The response of `POST /api/v1/jobs` has the stored `created_at` and `updated_at`. Before, they were `0001-01-01T00:00:00Z` (#88).
- `DELETE /api/v1/clusters/purge` also removes a cluster with an empty name that no job uses. Earlier versions accepted such a cluster, and no URL could delete it (#88).
- `ca_file`, `cert_file` and `key_file` must be regular files of at most 1 MiB. A FIFO, device, directory or larger file is rejected. Creating, updating or testing a cluster answers HTTP 400 when a set file exists and fails this check. A path that does not exist yet is still accepted at save time and fails when a client is created, as before. The cluster probe is unjoinable when a TLS file cannot be read, and the cluster is probed again (#76).
- Kafka clusters can use a private CA and mTLS. `ca_file`, `cert_file` and `key_file` in `security_config` of a cluster, or in `security` of a config file cluster, set the CA certificates and the client certificate and key of the TLS connection. Without `ca_file`, the system trust store is used as before. Creating, updating or testing a cluster answers HTTP 400 when only one of `cert_file` and `key_file` is set, or when one of them is set on a cluster without TLS. The Helm chart mounts a Secret named in the new value `kafkaTLS.existingSecret` at `/app/kafka-tls` (#76).
- Job routes for an unknown job ID answer HTTP 404 with `Job not found`, including `GET /api/v1/jobs/{id}/topic-health`, `DELETE /api/v1/jobs/{id}`, start, stop, pause, restart, mappings, metrics, lag, AI, inventory snapshots and the mirror state routes. Before, some of those calls answered HTTP 500 or an empty list, and `DELETE` answered HTTP 204 (#76).
- Job and cluster routes answer HTTP 404 only when the job or cluster does not exist, and HTTP 500 with `Failed to get job` or `Failed to get cluster` when the database cannot be read. `GET /api/v1/jobs/{id}/metrics/current` answers HTTP 500 with `Failed to get current metrics` when the database cannot be read, and HTTP 200 with zero totals for a job without reports. Before, a database error on these routes answered HTTP 404, so it looked like a missing job or cluster (#76).
- The cluster probe fingerprint includes an HMAC-SHA256 of the contents of `ca_file`, `cert_file` and `key_file`, so replacing a certificate at the same path starts a new probe. A file that cannot be read, or a cluster config that cannot be encoded, makes the check unjoinable and the cluster is probed again (#76).
- `mirror-cli users reset-password --password-file <path>` no longer prints the path it was given, also not in an error. Without `--password-file`, it prints the path of the new temp file as before (#76).
- The generated CLI docs show a flag without a short form as `      --name` instead of `-, --name` (#76).
- The Swagger reply text of HTTP 503 from `GET /api/v1/clusters/{name}/status` now comes from the handler annotation, so `make docs` no longer drops it (#76).
- Cluster status is stored. kaf-mirror checks every cluster that is not `inactive` or `archived` at start and then every 60 seconds, with a 10 second timeout per check and at most 4 probes at a time in the whole process (the background loop, `GET /api/v1/clusters/{name}/status`, checks after create, update or restore, and the pre-flight check of a job restart), and stores `active` or `unreachable`. Concurrent checks of the same cluster share one probe only when the connection settings still match, including provider, brokers, SASL and TLS settings, API key and secret, and the connection string. The probe fingerprint is an HMAC-SHA256 of the connection settings, keyed with a random key that exists only in this process, so the secrets are never stored or logged in plain text. If that key cannot be created, a check is never shared and the cluster is probed again. A slower check does not overwrite a later result or a result from a newer cluster configuration, and a cluster that is deleted and created again under the same name is treated as a new check. A new cluster is `unknown` until its first check. A check that is cancelled by a shutdown, or a status request cancelled while it waits for a probe slot, keeps the old status. `GET /api/v1/clusters/{name}/status` answers HTTP 503 when the live check fails (the stored status is `unreachable`). Inactive and archived clusters are not probed and the call answers HTTP 200. The background status loop does not run when `server.mode` is `test`. Before, the status was set only by `clusters remove` and `restore`, so the cluster list, the dashboard "Active Clusters" count, the topology and the `mirror-cli` dashboard showed `unknown` (#70).
- `mirror-cli clusters remove` without a name lists every cluster that is not already `inactive` or `archived`. Before, it listed only `active` clusters, so it found none while the status was never stored (#70).
- The `mirror-cli` dashboard shows `unreachable` clusters as errors and an `unknown` cluster as not checked yet. Its compliance panel shows the request method, path and user of each audit event instead of "Unknown by System", and the compliance list shows the resource path and details instead of empty columns (#70, #75).
- Every list endpoint answers `[]` instead of `null` when it is empty: the AI insights, anomalies and recommendations, the job AI insights, mappings, metrics history, inventory snapshots, topic health, mirror progress, resume points and gaps, the inventory topics, consumer groups and connections, the cluster topics, the events, the compliance reports, the clusters and the jobs. The arrays in `GET /api/v1/jobs/{id}/mirror/state?period=...` are `[]` too. The web UI treats `null` as an empty list, so the AI tab no longer throws `Cannot read properties of null` (#72).
- Web UI on phones: no tab is wider than the screen at 390px. The header wraps, the tab bar scrolls sideways, the job table turns into one block per job, and wide tables scroll inside their card (#75).
- Web UI topology: labels are larger and show the cluster status and role instead of a guessed region, several jobs between the same two clusters get their own curved edge, active jobs are drawn solid and animated, and the zoom does not go below 60% (#75).
- Web UI job details: the batch size is shown in KB, the mirror state counts and sums every partition from `GET /api/v1/jobs/{id}/mirror/progress` instead of the first one, and falls back to the `mirror_progress` array from `GET /api/v1/jobs/{id}/mirror/state` without treating that array as a single partition. "Current Lag" is now "Consumer Group Lag", and the mirror state value is named "Source End Minus Target End" with a note on how it differs from the consumer group lag (#75).
- Web UI inventory: the topic count of each cluster is read from `total_topics`, the average replica count from `replica_ids`, the topic catalog lists each topic once with the side it is on, and consumer groups show their state and member count instead of a lag that the inventory does not store (#75).
- Web UI dashboard: "Avg Lag (ms)" is now "Avg Consumer Lag (messages)" and the "Latency" chart is now "Consumer Lag (messages)", because both show the consumer lag in messages (#75).
- The compliance CSV audit trail lists every audited change in the period: each successful `POST`, `PUT`, `PATCH` and `DELETE` API request and every `config_change` event, with its time in UTC, user, action and details. The configuration change count uses the same events. The report compares event times in UTC. Before, it looked only for `config_change` events, which nothing writes, so the audit trail was always empty (#75).
- `GET /auth/me` returns the permission names of the user's role. The web UI hides what the user cannot use: the compliance report buttons without `compliance:generate`, the access control list without `users:list`, "Refresh State" and "Retry" without `jobs:edit`, and the analysis buttons without `ai:analysis:trigger`. It does not load users, events or AI insights without the matching permission. Before, a `monitoring` user saw the report and "Refresh State" buttons and got HTTP 403. The analysis buttons read the role from the wrong storage, so they were never shown (#75).
- Web UI clusters tab: a new table lists each cluster with its provider, role, status and the time of the last status change (#70, #75).
- Web UI activity log: it shows the 50 newest events, newest first. Before, it took the oldest 50 of the 100 returned events (#75).
- Web UI job details: a resume point at offset 0 is shown as `topic pN @ 0`, not as `N/A` or an em dash (#75).
- Inventory snapshots store the security protocol and SASL mechanism the cluster really uses. Before, every connection was stored as `SASL_SSL` with `PLAIN`, so a plaintext cluster showed as SSL in the web UI.
- Replicated records keep the source timestamp. Before, the target record got the time of the copy (#27).
- Replicated records keep the source partition. The producer now writes each record to the partition it came from. Before, the producer default partitioner chose the target partition (#28).
- A record whose produce fails is no longer skipped with its offset committed. kaf-mirror tries it up to 5 times, waiting 1s, 2s, 4s and 8s between the attempts. If the fifth attempt fails, the job stops with status `failed` and the source offset stays at that record. Stopping a job while the target is down no longer hangs and does not commit the waiting record. See "Resilience and Buffering" in the README (#32).
- A job that hits the producer error limit, a regex mapping that topic discovery cannot apply, or a panic no longer hangs as `active` and keeps its partitions. It stops, leaves the source consumer group and is marked `failed` with the reason. A failure of an instance that was already stopped or restarted is ignored, so it no longer stops the new instance or marks the job `failed`. Restarting a failed job clears `failed_reason`. Before, the job showed `active` with the old reason. See "Failed Jobs" in the README (#33).
- A topic discovery run that fails because the source or target cannot be reached, or because a new target topic cannot be created, no longer stops the job. kaf-mirror logs a warning, keeps copying the topics it already has and tries again at the next discovery run. Stopping a job while discovery waits to retry a topic creation no longer blocks for up to 15 seconds. See "Topic Discovery During an Outage" in the README.
- The Docker image starts with the documented `docker run`. It creates `/app/data` and `/app/logs` owned by the kaf-mirror user, declares both as volumes and sets `KAF_MIRROR_SERVER_HOST=0.0.0.0`, so the published port answers. `configs/default.yml` keeps `localhost` for runs outside Docker. `make dev-up` uses named volumes, because bind mounts created by Docker were owned by root and the server could not write to them (#34).
- The bootstrap admin password file is written next to the database, for example `/app/data` in the container, instead of the system temp directory. It now survives a container restart. The README shows how to read it with `docker exec` or `kubectl exec` (#34).
- The default Helm install starts. The chart sets `server.allow_insecure` from `config.server.allowInsecure` (default `true`) and can take the TLS certificate and key from a Secret with `config.server.tls.existingSecret`. Before, the pod crashlooped because production mode requires TLS (#35).
- The Helm chart uses the `Recreate` strategy, so two pods never open the SQLite database at the same time, and the render fails if `replicaCount` is not 1. It drops values from another project (the `qip.*` topics, the `job_id`, the `ops-foundation` label and the unused `source_cluster`, `target_cluster`, `topics` and `metrics.port` keys), adds `secretEnv` for tokens from a Secret, and now reads `tolerations` and `affinity`. When TLS is on, the ServiceMonitor scrapes HTTPS. CI lints and renders the chart (#52).
- An exact topic name with a dot, such as `pay.v1`, is no longer treated as a regex, so it no longer also copies `pay.v1.dlq`, `my-pay.v1` or `payXv1`. A pattern is a regex only when it has a regex character other than the dot (`\ ^ $ * + ? ( ) [ ] { } |`), and a regex must match the whole topic name. One shared resolver applies this rule at job start, in topic discovery, when routing records, in the mirror state, verify, lag and topic health views, and when mappings are saved. An exact mapping now wins over a regex for the same topic. See "Topic Mappings" in the README (#37).
- Missing target topics are created again. A topic counted as existing when the broker listed it with an error such as `UNKNOWN_TOPIC_OR_PARTITION`, so job start and discovery skipped the creation and then failed. Now only topics listed without an error exist, `TOPIC_ALREADY_EXISTS` from the create call counts as success, and after a create kaf-mirror waits until the topic is visible in metadata before the start check re-reads the cluster (#38).
- A regex mapping without a target keeps the topic names (`$0`). Before, the target became the pattern itself and the job failed with `target topic app-.* is mapped from multiple sources` (#39).
- `replication.topic_discovery_interval` is used. Before, every job discovered new topics every 5 minutes whatever the config said. A failed discovery run is retried at the next configured interval (#40).
- The mirror state, the start check of a force restart, mirror verify, resume points and the topic health checks resolve regex mappings to the matching topics. Before, they asked the broker for a topic named like the pattern, for example `app-.*`, and got `INVALID_TOPIC_EXCEPTION` (#46).
- `GET /api/v1/jobs/{id}/lag` finds the source cluster of the job in the database and reads the lag of the job consumer group `kaf-mirror-job-<id>` for each matched topic. Before, it looked for the cluster in the config file and answered 404, used the wrong group name and passed the group and topic in the wrong order.
- Creating a job or saving mappings with a regex that does not compile is rejected with HTTP 400 instead of failing at job start.
- If the target topic has fewer partitions than the source while a job runs, records from the missing partitions fall back to key hash placement and kaf-mirror logs one warning per partition. See "What a Copied Record Keeps" in the README.
- SASL from `security_config` works for every Kafka client. The consumer, the producer, the admin client, `POST /api/v1/clusters/test`, the topic list and detail views, the cluster status check, resume points and the inventory snapshot now build their options with one function, `kafka.ClientOptions`, that handles TLS, SASL PLAIN, SCRAM-SHA-256, SCRAM-SHA-512, GSSAPI and the `confluent`, `azure` and `redpanda` presets. Before, the admin client and the connection test only knew the provider presets, so a cluster with generic SASL failed the test and every admin call while its jobs could still connect (#36).
- `POST /api/v1/clusters/test` passes the full security config: the fields of `security_config` and of an optional `security` object. Before, it kept only `api_key` and `api_secret`. The test now gives up after 15 seconds (#36).
- SASL GSSAPI logs in with a keytab. New keys `security.kerberos.principal`, `security.kerberos.keytab_path` and `security.kerberos.krb5_conf_path` are file paths, never inline secrets, and `service_name` defaults to `kafka`. Before, GSSAPI had no Kerberos client and could not authenticate. The README removes the `jaas_config` example, which kaf-mirror never read. The Helm chart can mount the keytab from a Secret and `krb5.conf` from a ConfigMap (`kerberos.*`) and takes `config.sourceSecurity` and `config.targetSecurity`. See "Kafka Cluster Authentication" in the README (#36).
- Creating or updating a cluster answers HTTP 400 when `security_config` is not a JSON object, the SASL mechanism is unknown, a username or password is missing, or a GSSAPI cluster lacks the principal, keytab path or `krb5.conf` path (#36).
- Creating, updating or testing a GSSAPI cluster validates the Kerberos settings when `enabled` is omitted. Before, security was turned on only for an API key, a username or a password, so a GSSAPI config without `enabled: true` was saved and the connection test ran without SASL (#36).
- `POST /api/v1/clusters/test` uses the request context for its 15-second timeout, so a cancelled request does not keep the test running.
- When the Kafka client cannot be created after its SASL GSSAPI login was set up, for example because a broker address has no valid port, the consumer, producer, admin client and connection test now close the Kerberos client. Before, it was left open.
- A `confluent` cluster, or a `redpanda` cluster with a username, whose `protocol` is `SASL_SSL` no longer fails to create its consumer and producer with `cannot set both Dialer and DialTLSConfig`.
- The consumer and producer of an `azure` cluster use TLS and SASL PLAIN with the connection string. Before, only the admin client did, so jobs on Event Hubs could not connect.
- `POST /api/v1/jobs/{id}/mirror/resume-points` uses the full stored security config of both clusters. Before, it kept only `api_key` and `api_secret`.

- The inventory snapshot taken at job start is written to the database the server runs with. Before, it opened a second connection by path through a package global, so a job started from tests or embedded code created `data/kaf-mirror.db` in the working directory, and the snapshot failed with `FOREIGN KEY constraint failed` because that database had no such job. The consumer group part of the snapshot reuses the admin client of the start check instead of opening a new connection to the source cluster (#51).
- A job no longer waits for the target to acknowledge each record before it sends the next one and commits each record on its own. It sends all records of a fetch, waits for all acks and then commits the highest acked offset of each partition in one call. A failure commits its partition only up to the last acked record before it, retries the failed record and the records after it in order with the same 5 tries and waits, and fails the job when the tries run out. Stopping a job commits the records that were already acked. A partition that is revoked or lost is not committed. See "Batching" in the README (#50).
- The job fields `parallelism` and `preserve_partitions`, the config key `replication.parallelism`, the `mirror-cli config edit replication parallelism` command and the matching prompts were removed. kaf-mirror never used them: records are always written to their source partition, and the records of a fetch are now in flight together. Requests that still send the fields are accepted and the fields are ignored. The database columns stay, so no migration is needed (#50).
- On `SIGTERM` or `SIGINT`, kaf-mirror stops all running jobs, so they commit what the target acked, close their Kafka clients and leave the source consumer group, and then stops its background work. The jobs keep the status `active` and resume on the next start. Before, kaf-mirror only stopped the API server and exited, so the jobs never left the group and the next member waited for the session timeout. The API server and the jobs stop at the same time within the new `server.shutdown_timeout`, default `30s`, also `KAF_MIRROR_SERVER_SHUTDOWN_TIMEOUT`. A job that starts during shutdown is not started. Before, the API server shutdown had no time limit and could wait for open connections forever. The Helm chart sets `terminationGracePeriodSeconds` from a value (default 45) and `server.shutdown_timeout` from `config.server.shutdownTimeoutSeconds` (default 30), and the render fails if the grace period is not longer. `docker-compose.yml` sets `stop_grace_period: 45s`. See "Graceful Shutdown" in the README (#42).
- A dynamic throttling restart no longer waits while holding the job manager lock, so a SIGTERM shutdown is not delayed, and the job is not started again once shutdown has begun (#42).
- Job metrics no longer grow after a restart. Each run of a job reports its counters since it started, and kaf-mirror now stores the growth since the last report of the same run. Before, it compared the report with the stored lifetime total and, after a job or process restart, stored the whole in-memory count again on every 10-second report, so `messages_replicated` and the byte counts in `/metrics/current`, the dashboard, AI analysis and compliance reports grew without new records. See "Job Metrics" in the README (#43).
- `messages_replicated` and `bytes_transferred` count each source record once, when the target first acks it. Before, a record that was written again during a retry of an earlier record in the same partition was counted again (#43).
- The automatic halt checks compare the reports of one job only, and a job restart starts a new window. Before, the reports of all jobs went into one 60-second window, so the tombstone, error and payload checks compared the counters of different jobs and of an old and a new run (#43).
- `GET /api/v1/jobs/{id}/lag` returns the real lag of the job consumer group: for each partition the end offset minus the committed offset, a partition without a commit counted from its log start offset, and never below 0. It also works for a job that never committed. Before, it always returned 0 (#44).
- Topic configs are read when kaf-mirror lists a cluster, so the compression logged at job start, the compression mismatch warnings and the topic inventory show the real `compression.type`. Before, they always showed `NONE`. If the configs cannot be read, kaf-mirror logs a warning and reports `NONE` as before. The topic detail view uses the same code (#47).
- `tombstone_count` is stored and returned by `GET /api/v1/jobs/{id}/metrics/current`, and the job details in the web UI show it. `GET /api/v1/jobs/{id}/metrics/history` returns `tombstone_count_delta` for each report. The new column `aggregated_metrics.tombstone_count_delta` is added at startup when it is missing, with 0 for old rows. Before, it was always 0 (#48).
- `Error spike detected` is logged once when new produce errors come in, and again only after a report without new errors. `error_spike` in the metric sinks is true only for a report with new errors. Before, one error logged the line every 30 seconds for the life of the job (#49).
- `GET /api/v1/jobs/{id}/metrics/current` returns an error when the database cannot be read. Before, a failed read of the last report was ignored.
- The swagger docs list the response of `GET /api/v1/jobs/{id}/metrics/history` as `database.AggregatedMetric` and include `server.shutdownTimeout`.
- `GET /api/v1/jobs/{id}/lag` counts a partition from its log start when the committed offset is below the log start, for example after `DeleteRecords`. Before, it used the stale commit and overstated the lag (#44).
- `GET /api/v1/jobs/{id}/lag` uses the request context with a 15s timeout. Before, it used `context.Background()` with no deadline.
- `source_stalled` is true only when the job has lag and no new acks or commits for 60+ seconds. An idle job with lag 0 does not stall, and a stall can clear and fire again after traffic stops. Before, it fired for the life of the run once no record had been committed since start. `target_stalled` stays false, because consumed counts only rise after a target ack and a source commit, so a stuck target is reported as `source_stalled`. The `kaf_mirror_incident_target_stalled` gauge is kept and stays 0.
- The unused copies of the swagger spec at `web/docu/docs.go`, `web/docu/swagger.json` and `web/docu/swagger.yaml` were removed. The UI and the embedded spec use `web/docu/swagger/`.
- AI analysis is opt-in. Without `ai.provider`, kaf-mirror makes no AI requests and has no default endpoint, the AI analysis loops do not run, and it logs `AI analysis is off: ai.provider is not set` at start. An unknown provider, or `custom` without `ai.endpoint`, also leaves AI off. The AI endpoints that start an analysis answer HTTP 503 with `AI is not configured`. Before, a config without an `ai` section sent job names and metrics to `api.openai.com` every few minutes (#45).
- `ai.self_healing.automated_remediation` force-restarts a job with zero throughput even when no AI provider is set. `ai.self_healing.dynamic_throttling` also makes no AI call and still runs without one (#45).
- File and environment AI settings (`ai.provider`, `ai.token`, `ai.endpoint`) are used when they are set. A config saved in the database is used only when those file values are empty, so `KAF_MIRROR_AI_TOKEN` and a file provider still work after `PUT /api/v1/config` (#45).
- A self-hosted AI endpoint on a loopback or private address, such as Ollama or vLLM, is allowed. Link-local and cloud metadata addresses stay blocked (#45).
- The AI performance prompts no longer mention `parallelism`, which kaf-mirror does not have (#45).
- The Helm chart has `config.ai.provider`, `config.ai.endpoint` and `config.ai.model`, empty by default, so AI can be turned on in Kubernetes (#45).
- `clusters.<name>.disable_idempotent_writes` in the config file is applied to jobs whose stored target cluster has the same name. Before, jobs used only the clusters in the database, so the key was never applied and only `KAFMIRROR_DISABLE_IDEMPOTENT_WRITES` worked (#54).
- `admin-cli users add` asks for the password without echo when `--password` is left out, so it does not have to be on the command line (#54).
- The config keys `server.admin_email`, `logging.max_size`, `logging.max_backups` and `logging.max_age` were removed, because nothing read them. kaf-mirror does not rotate its log file. `replication.job_id`, `replication.batch_size`, `replication.compression`, `topic_mappings` and `protection.refuse_write_to_prod` are no longer read from the config file. Jobs always used their own stored settings, and refusing writes into a `prod` cluster is always on while protection is on. The keys were removed from `configs/default.yml`, `configs/docker.yml` and the Helm ConfigMap, together with the unused `topics` list in `configs/docker.yml`. An existing config file that still has those keys starts as before; the keys are ignored. This is not a breaking change to config loading (#54).
- The Helm chart can set `config.monitoring.enabled`, `config.monitoring.platform`, `config.monitoring.prometheus.pushGateway`, `config.protection.enabled`, `config.protection.autoHalt.enabled` and `config.egress.allowedHosts`. Those keys are written into the ConfigMap so `KAF_MIRROR_*` overrides work (#54).
- `admin-cli users add` reads the password from piped stdin when there is no TTY, so it works in scripts without putting the password on the command line (#54).
- The `k8s/` manifests were removed. They used config keys kaf-mirror does not read, did not start with their defaults and had no shutdown grace period. The Helm chart is the supported way to run kaf-mirror in Kubernetes (#54).
- `make build` no longer changes the committed `docs/cli-commands.md` and `web/docu/cli-commands.html`. The protection command help is the source of the docs text, and the Swagger link in the generated HTML no longer has a random query string. `make docs-check` regenerates the docs and fails on a difference, and CI runs it (#54).
- The Docker image, `make build`, `make dev-up` and the release workflow build again. They compiled `cmd/admin-cli/main.go` as a single file, so `readPassword` from `password.go` was undefined. All builds now compile the packages `./cmd/kaf-mirror`, `./cmd/admin-cli` and `./cmd/mirror-cli`. The release builds moved into `make release-binaries`, and a new CI job runs `make binaries`, `make release-binaries` and `docker build` on every pull request. The release workflow uses `actions/checkout@v4` and `actions/setup-go@v5` (#64).
- `current_lag` is now the lag of the job consumer group, the same value as `GET /api/v1/jobs/{id}/lag`, so `source_stalled` fires when the target is down. Before, `current_lag` came from the last fetch and stayed 0 while the job waited for target acks, so a stuck target never set `source_stalled`. If the source offsets cannot be read within 5 seconds, the report falls back to the fetch lag. The stall window is seven 10-second reports, about 70 seconds. GetGroupLag copies the topic list so kadm cannot change the caller's slice (#65).
- `TestClientConstructionNeverLogsSecrets` passes when the tests run more than once in a process, for example with `go test -count=3`. The logger has a new `SetOutput`, and the test sends the log to its own file through it. Before, the logger was set up only once per process, so a second run read an empty file.
- The first start of a job on a new target topic no longer fails with `target topic <name> does not exist after creation attempt`. After creating the topic, the job start read the target metadata once, and that read could go to a broker that had not seen the topic yet. It now reads the metadata up to 5 times, waiting 1s, 2s, 3s and 4s, within the 60 second limit of the start checks (#66).
- A job created without `batch_size` gets the default of 1000 KB. Before, it was stored with 0 and could not start (`max record batch bytes 0 is less than allowed 512`). `POST /api/v1/jobs` and `PUT /api/v1/jobs/{id}` answer HTTP 400 for a `batch_size` below 0 or above 102400 KB. A job already stored with 0 starts with 1000, and its next update stores 1000. The README regex job example sets `batch_size` (#67).
- `PUT /api/v1/jobs/{id}` without `name` keeps the stored name. Before, it set the name to empty. An update with an invalid topic mapping is rejected before anything is saved. Before, the other fields were saved and then HTTP 400 was returned (#67).
- Dynamic throttling keeps increases at or below 10000 KB and decreases at or above 100 KB. Before, a decrease from 100 KB or less set a negative value, and repeated increases from 10000 KB grew past 102400, so the restarted job could not start. Optimize does not lower a job whose `batch_size` is already 5000 KB or more, so a value set up to 102400 stays (#67).
- `mirror-cli config edit replication batch-size` and the config wizard no longer write `replication.batch_size`. That key is not read from the config file. Set `batch_size` on the job with `mirror-cli jobs add` or the API (#67).
- `mirror-cli jobs add` asks for the batch size in KB and the dashboard shows it in KB. Before, both said messages (#67).
- One record that the target rejects no longer fails the whole batch of its partition. When more than one record of a partition fails in the same try, for example because the target rejected their produce batch with `MESSAGE_TOO_LARGE`, kaf-mirror sends them again one at a time. The records before the bad record are copied and committed, and `failed_reason` names the offset of the bad record. Before, it named the first record of the batch and none of the batch was copied. The 5 tries stay the same for a record that is too large (#69).
- The record size analysis is logged at `DEBUG` instead of `INFO` for every 100th record and every record over 2 KB, and is tagged with the job ID instead of the topic. At `INFO`, a job logs one compression hint per topic that has a record larger than 2 KB. The README says that kaf-mirror does not rotate its log file (#71).
- `admin-cli backup database` and `backup full` take a consistent copy with `VACUUM INTO`, so a backup of a running instance includes the writes that are still in `kaf-mirror.db-wal`. Before, they copied only the main database file and lost recent data, for example a cluster created a minute earlier (#68).
- Backup files are created with mode `0600` and `backup full` creates its directory with mode `0700`, whatever the umask. Breaking: a backup no longer overwrites an existing file: the command fails and leaves the file alone. Before, backups were `0644` and held password hashes and API tokens (#68).
- `admin-cli restore database`, `import database` and `import full` check that the source is a readable SQLite database, copy it next to the database with `VACUUM INTO`, remove the old `-wal` and `-shm` files and move the copy in place with mode `0600`. They take an exclusive, non-blocking flock on `kaf-mirror.db.lock` and hold it through the copy, cleanup and rename, so the server cannot start mid-restore. They fail if the server already holds the lock. A leftover `-wal` file after a crash does not block a restore. The lock does not see a process that opens the database without it, so stop kaf-mirror first. Before, they copied the file over the open database and left the old WAL file next to it (#68).
- The server takes `kaf-mirror.db.lock` before it opens the database and refuses to start, with a clear error, while a restore or another kaf-mirror process holds it. It creates the data directory with mode `0700` and the database, `-wal` and `-shm` files with mode `0600`, whatever the umask, including on an existing 0644 file (#68, #74).
- Database restore and import are supported on Linux and macOS. They are not supported on Windows (`os.Rename` cannot replace an existing file there). Release binaries of `admin-cli` and `kaf-mirror` stay Linux-only; developers on Macs can `go build` them (#68).
- `admin-cli restore config` and `import config` set mode `0600` on an existing target file before writing, so a previous `0644` config is not left world-readable (#68).
- Breaking: `admin-cli restore` and `import` fail with an error when there is no terminal to confirm, and take `--yes` for scripts. Before, they printed "cancelled" and exited with status 0. `tokens reset` now does the same (#68).
- `mirror-cli --help`, `-h`, `--version` and `-v` work without a terminal. Before, `mirror-cli` started the interactive shell before cobra read the flags, and the shell panicked with `no such device or address` when there was no terminal. `mirror-cli` without a command still starts the shell, and without a terminal it now prints an error and exits with status 1 without calling the server. `mirror-cli dashboard` without a terminal does the same. Other prompts that printed "cancelled" and exited 0 without a terminal now exit with a non-zero status, and `users reset-password`, `clusters remove` and `jobs delete` take `--yes` (#73).
- `mirror-cli login` reads the password from the first line of stdin when stdin is not a terminal (#73).
- Breaking: `mirror-cli users add` writes the generated password to a new mode `0600` file in the temp directory and prints the path. Before, it printed `[REDACTED]` and the password was lost. Its `--password` flag, which was never read, is removed. `users reset-password` prints the path of the password file instead of `[REDACTED]` and sets mode `0600` on an existing `--password-file` (#74).

## [1.3.0] - 2026-09-09
### Highlights
- Experimental admin replication halt so a compromised source is not copied onto the replica (`docs/protection.md`). Off until enabled.

- Dropped committed TLS private keys. Bind `server.host` (not `0.0.0.0`); TLS required in production unless `allow_insecure`.
- CORS uses configured origins. Login rate-limited. Password minimum 12 characters; password change revokes tokens.
- Dashboard HTML-escapes user-controlled text. WebSocket auth is Bearer-only.

### Fixes & operations
- Cluster purge route, Helm SQLite on the PVC, foreign keys/WAL, SASL on job clients, regex substitution, job lifecycle/deadlock fixes.
- Mirror verify uses source consumer-group lag, not cross-cluster high watermarks.
- Prometheus `/metrics` and Helm ServiceMonitor.

### Upgrade notes
